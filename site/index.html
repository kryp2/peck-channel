Pay per second, per call, from your own wallet.

peck.channel is the primitive for paying per second or per call between a wallet and a service, settled on BSV and never in anyone else's custody.

It is a spec, a smart contract and a client library that other Peck services build on. It does not host anything and it is not a payments product.

Read the spec Test vectors npm: peck-channel

Status in one line: the contract and the library are proven on mainnet; channels are switched off on peck.run and llm.peck.to for now. Details below.

## How it works, at a glance

  1. Open

    The wallet locks an amount in one transaction. The coins sit in a contract output. The service cannot move them on its own signature.

    on-chain · one transaction

  2. Use

    The service meters per second or per call. Each new running total is authorised by the user's wallet as a signed message with the amount and a higher nonce. An old total cannot be replayed, and the total can never pass what was locked.

    signed running totals · checkpoints on-chain when needed

  3. Settle

    Close: the service receives what was spent and the user gets the rest back. Or, after the expiry, the user alone takes the locked amount back with a timeout, with no service involved.

    on-chain · one transaction

Non-custodial

The wallet only ever signs a hash for the user's half. The service builds the transaction, signs its own half and broadcasts. No private key crosses the boundary.

Two keys to drain

Moving the spend forward needs the user's signature and the service's. The service cannot drain a channel alone.

Always a way out

After the expiry the user can reclaim the locked amount, less the miner fee, straight from the network. The channel can never lock funds permanently.

Bounded and replay-safe

Spend is capped by the locked amount. The nonce goes up with every step, so an old signed total is worthless.

## The spec in four boxes

The full text is PECK_CHANNEL_SPEC.md. This is the part you need to see whether it fits.

Contract fields and methods (LLMPaymentChannel)
FieldTypeMeaning
userPubKeyPubKeyThe user who funds the channel (a BRC-42 child key)
gatewayPubKeyPubKeyThe service operator. Must match its co-signing key
lockAmountbigintTotal locked, in satoshis. The output value stays constant across drains
amountSpentbigint, stateRunning total spent, advanced by each drain
paymentNoncebigint, stateReplay protection, incremented by each drain
expiryTimebigintUnix time after which the user may time out

drain(amount, nonce, userSig, gatewaySig) needs both signatures and moves the spend forward. close(userSig) pays the service what was spent and the user the rest, less the miner fee. timeout(userSig) works only after the expiry and returns the locked amount to the user, less the miner fee.

What the wallet signs 
drain:   ANYONECANPAY | SINGLE | FORKID
close:   ALL | FORKID
timeout: ALL | FORKID, nLockTime = expiry

sighash = sha256sha256(BIP143 preimage,
                       input 0)

user sig = wallet.createSignature({
  hashToDirectlySign: sighash,
  protocolID: [2, 'peck channel'],
  keyID, counterparty: 'self' })

The drain flags bind only the contract input and the new state output, so the service can pay the miner fee from a separate input without changing the channel value. A createAction from the wallet would add its own funding input and change output and break that binding, which is why the service builds the transaction and the wallet only signs.

The gateway HTTP contract
RouteDoes
POST /channels/openRegisters a channel the user has funded.
POST /channels/drainThe gateway builds the drain spend and returns its co-signature, the sighash, the amount and the nonce.
POST /channels/cosign-drainThe client posts the sighash it rebuilt; the gateway co-signs that.
POST /channels/submit-drainThe client posts the finished drain. The gateway verifies it, signs its fee input and broadcasts.
POST /channels/closeThe gateway returns the authoritative amount spent; the client builds the close and the user signs it.
POST /channels/submit-closeThe client posts the finished close. The gateway checks the split and broadcasts.
no routeTimeout. After the expiry the user broadcasts the reclaim straight to the network. No gateway is involved.

Broadcast goes through ARC. The reference implementation of these routes is peck-host (peck.run).

Rules that must not break

Sighash parity: the Go and the TypeScript sides must compute byte-identical digests, checked against the golden vectors. Both signatures are required to drain. Timeout is always the user's way out, so a channel can never lock funds permanently. Any change to how the sighash is built has to keep the parity check green.

off And why

  • peck.run: since 28 September 2026 the channel routes answer 503 in production. The gateway does not yet check on-chain that a channel it is asked to open is really funded (the spec lists this as a TODO). Until it does, accepting channels would mean serving on credit that may not exist. They come back when that check does.
  • llm.peck.to: the per-request receipt tier is built into the gateway and switched off. Wiring it to the live path is the remaining integration.

open Not done yet

  • The gateway helper in the client library still sends the old login (the caller's public key as a bearer token), which peck.run no longer accepts. It needs the challenge login, and the example drivers in settle-sidecar/ with it.
  • The Go code that implements the spec lives in peck-host, and llm-gateway has a parallel copy. Merging them onto one shared core is open.
  • The npm package ships TypeScript source, not a compiled build.
